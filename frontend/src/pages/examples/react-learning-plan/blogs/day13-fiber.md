# 第 13 天笔记：React 并发模式与可中断渲染

你的观察很仔细，这三种模式的时间对比基本反映了并发特性的优化效果。但你对“赋值时优化”的理解需要更精确一点：**优化并不是发生在赋值那一瞬间，而是发生在 React 决定何时执行渲染的那一刻。**

下面帮你把笔记打磨一下，让表述更贴近底层原理。

## 优化到底发生在哪里？

你的笔记说“赋值的时候优化”，这个说法容易让人误解为：`setState` 或 `useDeferredValue` 内部做了什么魔法让计算变快。实际上，计算量（过滤 5000 条数据）完全没有变，变的是**计算被触发的次数**。

更精确地讲：

### 1. `startTransition` 的优化点

```ts
startTransition(() => {
  setKeyword(value);
});
```

这里的 `setKeyword` **立刻执行了**（状态更新被调度了），但它被标记为“过渡更新”（transition update）。React 的调度器（Scheduler）会给它一个较低的优先级。

**优化发生在调度层面：**
- 如果在低优先级的 `setKeyword` 渲染还没完成时，用户又输入了新字符，React 会 **丢弃前面还没完成的低优先级渲染**，直接开始最新的渲染。
- 所以，快速输入 `"abc"` 时，可能只有 `"abc"` 这一次低优先级渲染真正执行了，中间的 `"a"`, `"ab"` 都被跳过。渲染次数减少，总耗时自然下降。

这就是为什么你看到时间从 3.7 降到了 3.2：减少了中间的无效渲染。

### 2. `useDeferredValue` 的优化点

```ts
const deferredKeyword = useDeferredValue(input);
```

`useDeferredValue` 不会立刻把 `input` 的最新值传给 `HeavyList`。它会：
1. 先用**旧值**完成一次“即时渲染”，让输入框马上显示新字符。
2. 然后调度一个**低优先级的重渲染**，把最新值更新到 `deferredKeyword` 中。

**优化同样发生在调度层面：**
- 如果输入飞快，React 会多次对 `useDeferredValue` 触发重渲染，但同样只有**最后那次低优先级渲染**会被完全执行，前面的都会被跳过。
- 而且 `useDeferredValue` 还有一个特性：如果新值与旧值相同（比如你粘贴了同一个词），它完全不会触发额外的渲染，节省得更多。

你看到的时间 3.0 接近最省的状态，很可能就是因为跳过的中间渲染更多。

## 优化后的笔记（建议替换原有描述）

> **React 并发优化核心：并不是让单次计算变快，而是通过可中断渲染和优先级调度，减少不必要的计算次数。**

- `startTransition`：把状态更新标记为低优先级，允许紧急更新（如输入）中断它，从而在快速输入时**跳过中间状态的计算**。
- `useDeferredValue`：让一个值“滞后”更新，React 在连续变化时会**自动跳过延迟值的中间版本**，只保留最后一次计算。
- 两种方式的本质都是**牺牲实时性换流畅度**：列表显示可以晚一点，但手指输入必须丝滑。

你的时间数据完美印证了这个原理：上限从 3.7 → 3.2 → 3.0，说明无效渲染被一步步压缩。这个结论完全可以写进你的第 13 天笔记里。

---

**最后补一句：** `useDeferredValue` 并不是“正常拿到 input 数据”，而是“刻意拿到一个可能过时的 input 数据”。它返回的值是旧的，直到 React 觉得有空了才更新。这点和你说的“正常拿到”刚好相反，它正是通过**暂时拿到旧值**来换取性能的。把这个点理解透，你就能准确区分它和 `startTransition` 的差别了。
