## 第 14 天笔记：React Fiber 架构深度总结（优化版）

### 一、Fiber 架构的本质

**一句话概括**：Fiber 将 React 的渲染从“递归不可中断的调用栈”重构为“链表可中断的遍历循环”。

**为什么需要 Fiber？**
传统的 React 15 使用递归调用栈渲染组件树，一旦开始就必须同步执行完毕。当组件树很大时，主线程被长时间占用，用户点击、输入等交互无法得到响应，造成页面卡顿。

Fiber 用**链表结构**替代调用栈，使得遍历过程可以在任意节点“暂停”，把主线程控制权交还给浏览器，之后再从暂停处“恢复”继续执行——这就是**可中断渲染**。

---

### 二、Fiber 节点的关键指针

每个 Fiber 节点都是一个对象，通过三个指针形成**可中断的链表遍历结构**：

| 指针 | 指向 | 作用 |
|------|------|------|
| `child` | 第一个子节点 | 实现“递”阶段的深度优先遍历 |
| `sibling` | 下一个兄弟节点 | 同一层级横向遍历 |
| `return` | 父节点 | 实现“归”阶段的回溯 |

遍历顺序（深度优先）：
```
开始 → 向下深入（child）→ 没有子节点时向右（sibling）→ 没有兄弟时向上返回（return）
```

这个结构让遍历可以在任意节点处中断并恢复，因为每个节点都保存了“下一步去哪”的信息。

---

### 三、渲染流程的两个阶段

React 的渲染分为 **Render 阶段**和 **Commit 阶段**，这是理解 Fiber 的关键。

#### 3.1 Render 阶段（可中断）

此阶段负责**计算变化**，不操作真实 DOM，因此可以随时中断和恢复。

| 步骤 | 方向 | 核心函数 | 做什么 |
|------|------|----------|--------|
| **递** | 向下遍历 | `beginWork` | 进入节点，执行 Diff 算法，标记更新类型（Placement/Update/Deletion），生成 effect 标签 |
| **归** | 向上回溯 | `completeWork` | 完成节点处理，创建或更新 DOM 节点，收集副作用链（effectList） |

此阶段生成的产物是 **workInProgress 树**和 **effectList（副作用链表）**，后者是 Commit 阶段的工作清单。

#### 3.2 Commit 阶段（不可中断）

此阶段**真正操作 DOM**，一旦开始必须执行完毕，否则用户会看到不完整的 UI。

| 子阶段 | 执行内容 | 注意事项 |
|--------|----------|----------|
| **BeforeMutation** | 执行上一次 `useLayoutEffect` 的**清理函数**（返回的销毁函数） | 此时 DOM 还是旧的，可以读取旧布局信息 |
| **Mutation** | 操作真实 DOM：插入节点、更新属性、删除节点 | DOM 已经变化，但不通过 `MutationObserver` 观察（React 使用内部机制同步执行） |
| **Layout** | 同步执行本次 `useLayoutEffect` 的回调 | **关键**：此时 DOM 已更新但浏览器尚未绘制到屏幕，可在此读取最新 DOM 尺寸/位置，做同步布局计算 |

**commit 阶段之后**，浏览器才能拿到新的 DOM 并绘制到屏幕上。

### 四、双缓存机制（Double Buffering）

React 同时维护两棵 Fiber 树，通过 `alternate` 指针互相关联：

| 树 | 职责 |
|----|------|
| **current** | 当前屏幕上对应的 Fiber 树（用于展示） |
| **workInProgress** | 正在构建的新 Fiber 树（用于计算变化） |

**切换流程**：
1. Render 阶段在 `workInProgress` 树上做 Diff 和标记。
2. Commit 阶段完成后，`workInProgress` 变为新的 `current`，原 `current` 被回收复用。

**优势**：
- 可以实现**无感知刷新**：用户始终看到完整稳定的 UI。
- **节点复用**：旧的 Fiber 节点直接被新树复用，避免重复创建对象，性能极高。
- 是并发模式的基础：中断后可以恢复，因为两棵树互相保存着对方的状态。

### 五、时间分片与调度

#### 5.1 核心思想
利用浏览器的**空闲时间**（通过 Scheduler 包的 `shouldYield` 检查）处理 Fiber 节点。每完成一个 Fiber 节点的工作，React 检查是否还有剩余时间（默认 5ms），如果时间耗尽就暂停，把主线程还给浏览器处理用户交互。

#### 5.2 Lane 模型
用**二进制位**（Lane）表示更新优先级：
- 用户点击、输入 → 高优先级（SyncLane）
- `startTransition` 包裹的更新 → 低优先级（TransitionLane）
- 离屏内容 → 最低优先级（IdleLane）

通过优先级调度，确保即使有大量更新在进行，紧急的交互也能插队执行。

#### 5.3 与并发模式的协同
- `startTransition`：给更新打上 TransitionLane 标记，可被高优先级更新打断。
- `useDeferredValue`：让某个值滞后更新，React 自动跳过中间状态的渲染。
- 两种方式都是利用时间分片和优先级，**减少不必要的渲染次数**，而非让单次计算变快。

---

### 六、批量更新的本质

React 18 之后，所有更新（包括 `setTimeout`、原生事件）**默认自动批量处理**。多个 `setState` 调用被合并到一次 Render 阶段中执行，Commit 阶段只执行一次 DOM 更新。

**`flushSync` 的作用**：强制打破批量更新，让包裹的更新立即同步完成（同步调用 Render + Commit），之后可以立即读取新的 DOM 状态。这是“逃生舱”，会影响性能，应当谨慎使用。

---

### 七、useState 更新的三种调度路径

| 更新方式 | 调度优先级 | 行为 |
|----------|-----------|------|
| 普通 `setState` | 正常优先级 | 与事件处理中的其他 setState 合并批量处理 |
| `startTransition(() => setState(...))` | 低优先级（Transition） | 可被紧急更新中断，跳过中间状态，类似防抖但发生在调度层 |
| `useDeferredValue(value)` | 自动低优先级 | 返回的值滞后更新，React 自动跳过中间版本，保留最后一次计算 |

> **理解要点**：`startTransition` 和 `useDeferredValue` 的优化不是让单次计算变快，而是通过跳过中间渲染来减少总计算量。
